### 실행 시간 나눠 보기 (프로세스 시작부터, ms)

```
엔진 준비 186 → 웹페이지 시작 260 → 스크립트 313 → 화면 구성 334 → 폴더 열림 342 → 그리기 370
```

- 0~186ms: Tauri가 창과 웹뷰를 만들고 macOS 앱 실행 과정을 거치는 시간. 이 중 iSee 코드(설정, 캐시 DB, 메뉴)는 8ms.
- 186~260ms: 웹뷰 프로세스가 뜨는 시간.
- 260~370ms: 화면 코드 로드와 첫 폴더 그리기 (110ms).

웹뷰를 쓰는 비용이 약 0.26초라 0.3초 목표를 넘는다 (PLAN 6장 A 항목). 대신 상주 모드(창을 닫아도 앱 유지, 맥 기본값)에서는 사진을 열 때 이 비용이 들지 않는다.

## 5. 비슷한 사진 정리 (4단계)

테스트 세트: `isee-bench gen-similar` — 12MP JPEG 장면 24개(5번째마다 한 장뿐인 장면). 장면마다 원본과 변형을 섞음:
옮겨 찍기(3% 이동+1픽셀 흐림), 흐림, 과노출(날아감 4~7%), 저노출, 노이즈, 똑같은 사본. 총 108장, 정답은 `truth.tsv`.
측정: `isee-bench similar <폴더>`

- 특징값 계산: 12MP JPEG 한 장 **17ms** (1024px로 줄여 디코딩). 폴더 108장 **0.45초 (초당 241장, 스레드 6개)**
- 두 번째부터는 저장된 값을 쓰므로 화면을 열자마자 결과가 나온다
- 슬라이더·기준을 바꿀 때 다시 묶는 시간: **2~13ms** (108장, 똑같은 파일 확인 포함)
- 분석이 도는 동안 썸네일 첫 화면 48칸: 혼자 103ms → 분석 중 128ms (+25ms). 분석은 "비슷한 사진" 화면이 열려 있을 때만 돌고, 뷰어·비교 화면을 여는 동안 멈추므로 평소 탐색·보기 속도에는 영향이 없다
- 앱 실행 시간: 4단계 전과 같음 (첫 화면까지 349~386ms)

| 묶는 정도 | 묶음 | 정밀도 (같은 장면끼리만 묶였나) | 재현율 (같은 장면을 다 찾았나) | 베스트 추천 정답 |
|---|---|---|---|---|
| 1 거의 같은 것만 | 19 | 100% | 52% | 19/19 |
| 2 아주 비슷한 것 | 20 | 100% | 70% | 20/20 |
| **3 비슷한 것 (기본)** | 20 | 100% | 86% | 20/20 |
| 4 조금 비슷해도 | 20 | 100% | 96% | 20/20 |
| 5 대충 비슷해도 | 20 | 100% | 96% | 20/20 |

- 베스트 정답: 원본·사본·옮겨 찍기(분석 해상도에서 원본과 같은 품질) 중 하나를 추천하면 정답
- 놓치는 것은 대부분 하늘이 크게 날아간 과노출 사진(원본과 지문 차이 8~24비트). 서로 다른 장면끼리는 가장 가까워도 22비트
- 플래그: 흐림 1장, 너무 어두움 5장(모두 저노출 변형), 너무 밝음 6장(모두 과노출 변형) — 잘못 표시된 사진 없음

## 9. 얼굴별 분류 (8단계)

테스트 세트: 미국 정부 공식 사진(퍼블릭 도메인) 6명 41장 — 위키백과·위키미디어 공용에서 받아 로컬에서만 사용 (저장소에 넣지 않음). 군중 사진 1장 포함.
측정: `isee-bench faces <모델 폴더> <사진 폴더>` (파일 이름 "사람_번호"를 정답으로)

- 모델 읽기 108ms (설치 후 처음 한 번)
- 사진 한 장: 디코딩 3.5ms · 얼굴 찾기 **15ms** · 얼굴 지문 **15ms/얼굴** (CPU 한 코어, tract)
- 백그라운드 작업 3개 (14코어 맥) 기준 추정: 사진 1만 장(얼굴 평균 1.5개) 약 2~3분

| 비교 | 결과 |
|---|---|
| 같은 사람 쌍 123개 | 중간값 0.75, 기준 0.40 이상 94% |

앱에서 확인 (iSee.app 배포 빌드):
- 설치: 37MB 내려받기·SHA-256 확인 → 41장 분석까지 10초 이내
